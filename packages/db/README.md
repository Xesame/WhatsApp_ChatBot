# @reb/db

Database schema, migrations, connection pool and seed data.

| Path                    | What it is                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| `src/schema/`           | Drizzle table definitions: the source of truth for the database structure                 |
| `src/schema/docs.ts`    | Plain-English description of every table and column (feeds the generated docs)            |
| `migrations/`           | Plain SQL migrations, generated by drizzle-kit and committed. Read them before deploying. |
| `src/client.ts`         | `createDatabase(url)`: the connection pool, a `ping()` for health checks, `close()`       |
| `src/migrate.ts`        | Applies pending migrations (`pnpm db:migrate`)                                            |
| `src/seed.ts` + `seed/` | Loads starter cities, developers, projects and aliases (`pnpm db:seed`)                   |

**Why it is designed this way.**

- **Migrations are SQL files you can read.** Every schema change goes through `pnpm db:generate` → review the SQL → commit → `pnpm db:migrate`. Nobody edits the database by hand (build plan, rule 7). Applied migrations are recorded in `drizzle.__drizzle_migrations`, so running migrate twice does nothing.
- **Aliases point at entities through three real foreign keys** (`city_id`, `developer_id`, `project_id`, exactly one set), not a generic "type + id" pair, so Postgres guarantees an alias never points at a deleted row.
- **The seed is idempotent and never deletes.** It matches existing rows by English name, updates the Arabic name, and skips aliases that already exist. Aliases added by hand or learned from the review queue survive re-seeding. Running it on every `docker compose up` is safe.
- **The seed is validated before it touches the database**: duplicate names, unknown developer/city references, or an alias pointing at two different entities of the same kind all stop the seed with a clear list of problems.
- **pg_trgm** is enabled by the first migration so aliases can be matched fuzzily (`'mivda'` finds `Mivida`).

**Changing the schema:**

```sh
# 1. edit src/schema/*.ts and document new columns in src/schema/docs.ts
pnpm db:generate            # writes migrations/NNNN_*.sql
# 2. read the SQL, then
pnpm db:migrate
pnpm run docs               # regenerates docs/generated/database.md
```

**Editing the seed:** edit `seed/cities.ts`, `seed/developers.ts` or `seed/projects.ts`, run `pnpm test` (validates the data) and `pnpm db:seed`. Don't rename an entity in the seed. That creates a second row. Rename it in the database instead (admin UI from Phase 5).
